# Threads reliability implementation

The source changes address verified offline recovery and publish retry defects. They do not establish what happened in a live posting day.

- Existing due delivery runs before generation and planning. Delivery and queue mutation passes remain sequential; newly scheduled future rows wait for the next tick. Planner failure is returned in `planningError` and marks worker attention independently of already completed sends.
- A completely missed existing batch can recover. Recovery keeps IDs, saved wording and approvals; it protects published, claimed, failed, attempted, uncertain and manually skipped slots across accounts. Future recovered slots use the catch-up spacing and cooldown, stop at the posting window, and leave room after a recent or uncertain send.
- A fresh container is durably saved with a pre-publish preparation timestamp. A separate durable attempt timestamp is saved before one `threads_publish` request. Network, timeout, HTTP 408/5xx, malformed JSON and missing/invalid receipt responses hold the send. HTTP 429 is held conservatively too. An explicit rejection clears the attempt guard, and a confirmed receipt clears it while retaining the container and post IDs.
- Parent and reply guards survive restart. Legacy containers lacking the new preparation timestamp are held because their prior publish phase is unknown. Retry, replan, skip and removal cannot erase an uncertain send. The skip route atomically rejects a pending post after its parent delivery is claimed or carries container, attempt or receipt evidence; an untouched skip still wins before the claim. Reschedule and batch shift also leave started parent rows untouched, including their claim and original time. A batch shift still moves other unstarted pending rows, and reports an error when only started rows remain. History retention keeps unresolved containers/guards. Accepted receipts survive a failed save through the existing memory recovery path; after a process restart the durable attempt guard prevents a replay when that receipt never reached disk.
- Schedule jitter stays inside the configured window. Account staggering is included when deciding whether every account's version fits, and start-now planning reserves that time. A boundary slot that cannot fit every account is dropped for every account rather than spilling past the stop.
- Skipped-only days, and days with distinct fully sent and fully skipped ideas, no longer display “all sent.” The existing calendar rollup remains unchanged: one idea published on one account and skipped on another still rolls up as sent. Four new fallback idea pairs offer grounded workflow and small-business suggestions. The central brand kit and AI prompt wording are unchanged.

## Limits and ownership

No live posting, production files, credentials, OAuth, task registration, paid generation, deployment, release or merge was used. Tests use isolated data directories and mocked platform responses. The source and documents do not change the frozen desktop or website conversion paths.

Uncertain sends require owner reconciliation against Threads; there is no fabricated provider lookup, automatic resend or new override. Conservative holding may reduce delivery until the owner resolves a missing receipt or legacy container. The scheduler request still awaits planning after the delivery pass, but the existing queued posts are processed before that wait. These tests establish local safety behavior, not production scheduler health, token validity, live engagement or conversions.

The owner decides when to install/rebuild/restart the running app. This implementation agent releases its worktree only after its source commit and validation receipts are handed to the parent for review and documentation integration.
