# Source project creation contract

This adapter is dormant unless the owning Node process supplies an explicit creation policy. No policy, credential, runtime installation or hosted connection is enabled by this change. The original desktop service and its records remain authoritative.

`GET /api/integrations/marketing/editor/{projectId}/creation` requires the verified owner and both read and write scopes. It returns a passive exact context or null when no policy permits creation. The context binds the existing static root, policy ID/version, a separate creation revision, original source identity, cached-caption digest and whether that cache is absent or present. It exposes no file path or source bytes.

`POST /api/integrations/marketing/operations` accepts `create_editor_project_from_source` with that context and a UUID. The trusted policy selects an exact existing root/job/clip/source SHA, with at most 32 lifetime children. Callers cannot select a file, owner, child ID or new policy. The original store's queue, OS lock and atomic replacement commit the server-generated child and immutable root receipt together. Exact command replay returns the same child ID without rewriting the document; a changed payload or stale creation counter conflicts.

Creation reuses the original New project picker's constructor, cached-caption window/chunking, title and title overlay. It is a fresh project from that candidate, not a duplicate of the root's manual edits. Root edits, review target, prepared artifact and export/cancellation history are preserved. Unrelated ordered rows and other document fields are preserved exactly. The original library may select the newer same-source child, consistent with its existing newest-project behavior.

Child reads and saves require the current policy, active static root, matching retained creation receipt/provenance and current source SHA. Child export requests and worker claims are forbidden in this slice; creation does not infer worker authorization. Refreshing the source transcript does not overwrite stored child caption corrections. Root deletion or policy revocation closes child access, while an exact root creation receipt remains recoverable without returning a child snapshot. The shared source media URL retains its independent static root grant; it is not a child-specific revocable media grant.

The public receipt contains only operation, commandId, rootProjectId, createdProjectId, revision, digest, renderSignature, policyId, policyVersion, creationRevision, reviewInvalidated:false, rootReviewPreserved:true and publicationAuthorized:false. Source hashes, cache proof and grant provenance stay private. If asynchronous preview projection fails after commit, the response retains that receipt with null childTarget/snapshot and a reconciliation reason. A final current-target/policy/source check follows projection. No fresh command or automatic retry is implied.

The source scan uses a fixed 256 KiB buffer and a 512 MiB byte ceiling, with regular-file, single-link, path and descriptor identity checks. Captions have 20,000-row, 100,000-word and 4,000,000-byte canonical limits, including a cheap preparse text bound. This synchronous full source check is bounded but can be expensive for large clips; hosted performance and concurrency remain unmeasured. It performs no decode, network call, transcription or publishing action.

Validation uses synthetic original documents and actual HTTP handlers, including creation after a real mixed image/music render, unchanged prepared root access, duplicate and stale commands, foreign/read-only callers, revoked policy during projection, failed atomic replacement, lost replies, source replacement, corrected captions and generic writer preservation. Exact reports and the retained restricted-filesystem failure are recorded in the checkpoint; local fixture proof is not hosted or provider proof.

Remaining work is explicit: no browser creation control, active creation policy, child worker binding, Split implementation, new upload path or hosted transport. The separate mobile worktree and accepted design are untouched. Activation and installation require their own scoped approval, and social publication requires content/platform-specific authorization.
